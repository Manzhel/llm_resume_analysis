# LLM-cистема анализа резюме для рекрутеров

Система помогает рекрутеру структурировать данные кандидата: извлекает и классифицирует навыки,
фиксирует текстовые подтверждения и (если передана вакансия) сопоставляет профиль с требованиями.

> Система не принимает решение о найме.
> Она показывает только сведения, найденные в предоставленном тексте, и оставляет решение рекрутеру.

## 1. Назначение, входы и выходы

**Вход:** текст резюме/анкеты кандидата; необязательный текст вакансии.

**Выход:** JSON:
- краткое описание профиля;
- список навыков с нормализованным названием, категорией, уровнем, evidence и confidence;
- образование и опыт, если явно указаны;
- сопоставление требований вакансии (match / partial_match / not_found / unclear);
- рекомендации и ограничения анализа.

**Основные операции:**
1. извлечение и классификация навыков кандидата;
2. извлечение требований вакансии;
3. сопоставление навыков и требований.

Сценарии: первичная структуризация резюме, поиск кандидатов по группам навыков,
подготовка краткой карточки кандидата, предварительная проверка соответствия вакансии.

## 2. Архитектура и обоснование

### One-shot baseline
Один LLM-вызов получает резюме и вакансию и возвращает единый JSON со всеми результатами.
Преимущество — меньше задержка и стоимость. Недостаток — модель одновременно решает несколько
задач, поэтому сложнее локализовать ошибку и проверять промежуточные результаты.

### Multi-step workflow (Sequential)
```text
Резюме ──> [LLM 1: извлечение и классификация навыков] ──┐
                                                       ├─> [LLM 3: сопоставление] ─> JSON
Вакансия ─> [LLM 2: извлечение требований] ────────────┘
```
Workflow (Sequential) выбран потому, что извлечение навыков и требований — логически самостоятельные задачи,
а этап сопоставления зависит от их результатов. Между этапами передаются проверенные Pydantic-модели.
Если вакансия не передана, система формирует профиль кандидата и явно помечает matching как
`not_assessed`. Ошибка API, невалидный JSON или несоответствие Pydantic-схеме приводит к контролируемой
ошибке, которая записывается экспериментальным скриптом.

## 3. Установка

Требуется Python 3.10+.

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

Скопируйте `.env.example` в `.env` и заполните `OPENROUTER_API_KEY`.
При необходимости поменяйте `OPENROUTER_MODEL` на модель, доступную в вашем аккаунте OpenRouter.

## 4. Запуск

Из корневой папки проекта:

```bash
python main.py --candidate samples/candidate.txt --vacancy samples/vacancy.txt --mode one-shot
python main.py --candidate samples/candidate.txt --vacancy samples/vacancy.txt --mode workflow
```

Без вакансии:

```bash
python main.py --candidate samples/candidate.txt --mode workflow
```

Результат сохраняется в `results/last_result.json`.

## 5. Тестирование и эксперимент

В `evaluation/test_dataset.json` находится 12 тестовых примеров.

Запуск одинакового набора для обеих реализаций:

```bash
python -m evaluation.run_experiments
```

Скрипт измеряет:
- долю успешных выполнений;
- precision, recall и F1 для извлечения навыков относительно эталонных списков;
- среднее время;
- число LLM-вызовов;
- среднее количество токенов по данным API.


## 6. Результат тестирования


| Метрика | One-shot | Workflow |
|---|---:|---:|
| Доля успешных выполнений | 100% | 100% |
| Средний F1 навыков | 0,678 | 0,88 |
| Среднее время, с | 30,75 | 52,18 |
| Среднее число LLM-вызовов | 1 | 3 |
| Среднее число токенов | 3488,5 | 5386 |

Переход от архитектуры One-shot к Workflow привёл к повышению качества извлечения и классификации навыков кандидатов.  Workflow в среднем лучше справлялся с выделением релевантных навыков и уменьшал количество ошибок при их классификации и сопоставлении с требованиями вакансии. Но Workflow оказался более ресурсоёмким подходом.

### Анализ расхождения архитектур
В резюме указаны навыки Python, SQL и Power BI. В вакансии требуются Python, SQL и Tableau.

One-shot: модель одновременно анализирует резюме и вакансию. Из-за высокого совпадения основных навыков она оценивает соответствие кандидата как высокое.

Workflow: сначала формирует отдельный профиль кандидата, затем извлекает требования вакансии и только после этого сопоставляет их. При таком подходе отсутствие Tableau выделено как недостающий навык, а соответствие оценено как среднее.

## 7. Анализ результатов

1. Улучшилось ли качество решения при переходе к Workflow?

Да. Средний F1 увеличился с 0,678 до 0,88. Это свидетельствует об улучшении качества извлечения и классификации навыков, а также сопоставления профиля кандидата с требованиями вакансии. Доля успешных выполнений осталась одинаковой и составила 100%.

2. Как изменилась производительность и стоимость обработки?

Workflow стал работать медленнее: среднее время увеличилось с 30,75 до 52,18 секунды. Количество обращений к модели выросло с одного до трёх, а среднее количество токенов — с 3488,5 до 5386. Следовательно, повышение качества сопровождается увеличением вычислительных затрат и потенциальной стоимости API-запросов.

3. Какие ошибки возникают в системе и как они влияют на результат?

В ходе разработки и тестирования были выявлены следующие типы ошибок:

Ошибки классификации навыков. Модель может относить навык к неправильной категории, что снижает точность результатов.

Ошибки нормализации. Один и тот же навык может быть представлен разными названиями или формулировками. Это затрудняет сопоставление навыков кандидата и требований вакансии.

Ошибки интерпретации уровня владения навыками. Модель может неверно оценивать уровень компетенции на основании недостаточного описания опыта.

Ошибки формата ответа. На этапе разработки модель возвращала значения, не соответствующие структуре данных. Для решения этой проблемы была добавлена нормализация категорий и оценок, а также проверка ответов с помощью Pydantic.

4. Оправдана ли выбранная архитектура для вашей задачи?

Да. Workflow оправдан для системы анализа резюме, поскольку позволяет разделить задачу на отдельные этапы и повысить качество сопоставления навыков с требованиями вакансии.  Дополнительные затраты времени и токенов являются приемлемым компромиссом, если приоритетом является качество анализа кандидатов.

5. Какие ограничения есть у текущей реализации и что необходимо улучшить?

Текущая реализация имеет ряд ограничений:

качество анализа зависит от выбранной языковой модели и доступности API;

система может допускать ошибки при интерпретации неоднозначных формулировок;

словарь категорий навыков и механизм нормализации не охватывают все возможные профессиональные области;

отсутствует полноценная интеграция с базами резюме и системами управления подбором персонала.

Что можно улучшить:
1. фиксированная классификация навыков и словарь синонимов;
2. более строгие Structured Outputs и повторная валидация;
3. пакетная обработка резюме;
4. поиск по навыкам и фильтры для рекрутера;
5. RAG по корпоративному справочнику компетенций;
6. экспертная разметка.
